Architecture Evaluation · TypeBuild Client

Local-first, encrypted, and actually fast

The client already stores tasks in a local SQLite cache and paints Home from disk before the network answers. This evaluates why the encrypted copy silently drops to memory-only, why every launch pulls the entire task history from every group, and lays out a plan to make the front end feel instant — without weakening the at-rest security model.

Scope: read-first, no code changed Repos: breezefile · task_manager_api Verdict: local-first is the right base — three fixable gaps
01

Where we are today

✓

The foundation is sound. Tasks persist to a local SQLite cache split into two files: a plaintext skeleton (routing metadata — status, priority, assignee, project, timestamps) and an encrypted PHI store (SQLCipher, holding only title and body). On cold start the renderer paints synchronously from the plaintext skeleton — no key, no network — then layers real titles in as they arrive. That disk-first design is exactly right. The problems are all at the edges of it.

The cold-start sequence

What blocks the first paint is essentially nothing network-bound. But the real titles ride a slower, fragile path:

instant 1 · Skeleton read Plaintext SQLite → in-memory cache. Order, counts, filters all correct. No key needed.
instant 2 · First paint Home renders from the skeleton — but titles show as TypeBuild task ab12 placeholders.
fragile 3 · PHI hydrate Open the encrypted store (needs the OS keychain) → layer in real titles. Skipped entirely if the keychain is unavailable.
heavy 4 · Network sync Pull the entire visible inventory (every status, every group) to reconcile.

Steps 1–2 are the win already banked. Steps 3 and 4 are where the perceived speed and the real latency leak out.

02

The three problems, precisely

A Titles vanish on restart

The encrypted PHI store only persists when Electron safeStorage.isEncryptionAvailable() is true — i.e. an OS keychain (Keychain / libsecret / DPAPI) is present and unlocked. When it isn't, the store runs memory-only: titles never touch disk, and every cold start shows opaque placeholders until the network answers.

This dev box (LXQt, no keyring) hits it every launch.

B Every task, every launch

The sync always requests ?titles=1&all=1 — every status (including done/cancelled from a year ago) across every group the user belongs to. The server answers with a full-table scan, decrypting each row's title (and body, to derive a template flag). No limit, no recency cutoff, no group scope.

Latency + a Home cluttered with stale done tasks.

C No relevance scoping

Group membership is known authoritatively on the server and is fetched client-side only for the assignee picker. It is never used to scope what you see. The server already accepts group_id, status, and limit filters — the client uses none of them.

Users wade through other teams' work to find their own.
The uncomfortable truth about B

The server's list_tasks does SELECT * FROM tasks ORDER BY created_at — it loads the whole table, then filters visibility in Python row-by-row, decrypting each surviving title and body. The client's "pull everything" pattern makes that full scan run on every reconcile. The filters to fix this already exist on the endpoint; they're simply not being sent.

03

Why it drops to memory-only — and how to keep titles on disk securely

The encryption is deliberately strong. The SQLCipher key is HKDF-SHA256(master, deviceSalt, "typebuild-phi-db:" + principal) — three factors that must all be present:

  • A random master key — generated once per user, stored only wrapped by the OS keychain (safeStorage). The raw master never hits disk.
  • A device salt — a machine-local random file, binding the key to this machine.
  • The principal — the Firebase user id, namespacing the key and file so account A can never open account B's DB.
Why the fallback exists (and why it's blunt)

Because the master is random and keychain-wrapped, a stolen disk or backup is undecryptable — you'd need a live, authenticated OS session the keychain trusts. That's a genuinely good property. But there is no alternate key path. If the keychain is absent, the code refuses to persist rather than write a weakly-sealed key — so it falls all the way back to memory-only. Good security instinct, blunt failure mode.

The fix: add a second key path, keep the strong one as default

We don't weaken the keychain path — we add a tiered key-resolution ladder so "no keychain" degrades to "still encrypted on disk" instead of "nothing on disk." Best available factor wins:

TierKey sourceSurvives restart?Stolen-disk safe?When it applies
1 Keychain-wrapped master (today) Yes Strong Keychain present & unlocked (most macOS/Windows, GNOME/KDE Linux)
2 Session-token–derived key (new) Yes* Good No keychain, but a valid refresh/session secret exists on disk (already stored)
3 Passphrase-derived key (Argon2id) (new, opt-in) Yes Strong User sets an app passphrase; unlocks the store on launch
4 Memory-only (today's fallback) No n/a Nothing else available — last resort only

* Tier 2 is bounded by the session secret's lifetime — titles persist across restarts while signed in, and become undecryptable after sign-out. It reuses auth material the app already keeps, so it adds persistence on headless / no-keyring machines with no new secret to manage. Every tier still binds to the device salt + principal, so cross-machine and cross-account isolation are unchanged.

Why session-token-derived is NOT the obvious winner — even assuming FDE + login timeout

If the machine has full-disk encryption and a locked screen, the "stolen disk" threat the OS keychain guards against is already handled at the disk layer — so a token-derived key becomes far more defensible. But two things keep it from being the clear pick:

1. Login timeout turns into data loss, not just re-auth. The DB is encrypted with a key derived from the token. When the token rotates/expires, the old key no longer derives — the encrypted titles on disk go undecryptable, not merely "sign in again to view." You must re-encrypt the store on each new login (or keep a stable master the token only wraps, rotating the wrapper, not the key). Get it wrong and a timeout silently orphans the cache — worse than memory-only, which fails cleanly.

2. It couples two lifetimes that should be independent. The token proves identity to the server; reusing it to encrypt local data at rest means a server-side session policy (timeout, forced re-auth, revocation) silently governs whether your local titles are readable.

The honest conclusion: under FDE, a stable random master (keychain-wrapped when available, plain-wrapped in a 0600 file when not) gives the same transparent no-friction persistence with less machinery than the token-rotation dance — and a passphrase (Argon2id) is the only option that gives real at-rest protection independent of the OS session. Session-derived sits in an awkward middle: more code than the stable-master approach, weaker than the passphrase one. Recommended framing: keychain (transparent, where available) → stable-master (transparent, no keyring) → passphrase (opt-in, strong) → memory-only. Session-derived only if you specifically want "titles auto-lock when the session ends" as a feature, not as the default.

Design guardrail

The security invariant stays: no durable plaintext PHI on disk, ever. Tiers 2–3 keep the file encrypted; they only change where the unlocking secret comes from. The ladder is ordered by strength, picks the best available, and records which tier is active so the UI can nudge ("set a passphrase to keep your task names on this device").

04

Making the pull small — relevance + recency

The single biggest latency win is to stop pulling the whole history. Three changes, all using filters the server already supports:

Scope by the user's groups

Fetch the user's group set once (the /chromeext/groups endpoint exists), let them pick an active scope, and thread group_id into the list + poll requests. Tasks and projects narrow to what's relevant. This is both a latency win (smaller result set) and a UX win (you see your team's work, not everyone's).

Split "active" from "history"

Two-tier loading by recency:

  • Hot set — open + in-progress + needs-you + recently-finished (last N days). Small, fast, always synced. This is what Home shows by default.
  • Cold history — older done/cancelled tasks. Loaded lazily, on demand (a "show completed" / search-into-history action), never on the launch critical path.

This needs one small server addition — a recency cutoff (done_since / completed_after), since today done-hiding is status-based only, with no date filter. Pair it with limit for a hard ceiling on the first pull.

And on the server, while we're there

The full-table scan wants an index on updated_at (delta sync) and a visibility-aware query that filters in SQL rather than loading every row into Python. Deriving the template flag by decrypting every body on every list is the other hot spot — cache that non-PHI flag as a column so the list never touches the encrypted body. These are server tasks (filed against task_manager_api).

05

Sequenced plan

Ordered so each phase ships a felt improvement and de-risks the next. Client-only work first; server changes batched.

SHIPPED client · done

Recency-led roster + group plumbing ✓

The display-layer wins that needed no server change or security tradeoff — shipped.

  • Recency sort — the roster leads with most-recent activity, not source order.
  • Hide old done — tasks finished > 14 days ago are hidden behind a "Show N older" link; searching / filtering to Done always includes them.
  • Group-aware pagination — first 50 units with "Load more"; a template/chain group counts as one unit and never splits.
  • Group plumbing — groupId now flows server → view-model; useNewHomeData can scope by group and exposes the group list. The picker UI is the one remaining follow-up.
→ Home leads with live, relevant work — done, in a pure tested module; roster UI untouched.
NEXT client · S

Group scope picker

The one UI piece left from the relevance work — deferred only because the Home chrome was being reworked in parallel.

  • A listGroups() (id + name) on the source → bridge; a compact "All groups / <group>" picker in the topbar, mirroring the project picker.
  • Wires straight into the shipped useNewHomeData(projectId, {groupId}) seam + the groups list.
→ See one team's work at a time. Data layer already done.
PHASE 2 client · M

Tiered key ladder — persist titles without a keychain

Add tiers 2–4 to resolveDbKey so no-keyring machines keep encrypted titles on disk.

  • Tier 2: derive a wrapping key from the existing session/refresh secret (HKDF, same salt + principal binding).
  • Record the active tier; expose it so the UI can explain state and offer the passphrase upgrade.
  • Tier 3 (opt-in passphrase, Argon2id) can follow as its own slice.
→ Instant real titles on cold start, everywhere — not just keychain machines.
PHASE 3 server · M

Server: cheap lists

Batched task_manager_api work so the server stops paying for the full scan.

  • Index updated_at; visibility-scope + status/group/recency filter in SQL, not Python.
  • Store the non-PHI template flag as a column → the list never decrypts bodies.
  • Add a completed_after / done-recency cutoff so the hot set has a real date boundary.
→ The heavy reconcile (step 4) gets an order-of-magnitude cheaper.
PHASE 4 client · M

Optimistic writes + local-first mutations

Close the loop: make writes feel instant too, not just reads.

  • Apply mutations to the local cache immediately; queue the network write; reconcile on ack (roll back on failure).
  • Bound the local history so the skeleton DB doesn't grow without limit.
  • An offline/stale indicator so trust is never ambiguous.
→ No round-trip wait on any interaction. (Overlaps an existing epic — coordinate.)
06

Perceived speed — cheap wins beyond raw latency

Half of "fast" is feel. These are low-cost and stack on top of the real-latency work above.

Skeleton-shaped placeholders, not opaque ids

While a title hydrates, show a subtle shimmer block sized to the row — never TypeBuild task ab12, which reads as broken. The eye forgives a loading shape; it snags on a wrong value.

Paint the hot set first, stream the rest

Render open/needs-you rows the instant the skeleton loads; let done/history fill in below without blocking. The screen that matters is ready before the rest exists.

Persist last scroll + open state

Restore Home exactly where the user left it. Returning to a familiar frozen frame reads as "already loaded" even mid-sync.

Optimistic everything

Claim, start, edit — reflect the change locally on click, reconcile in the background. The action already happened as far as the user can tell.

Warm the cache before it's asked for

Prefetch a task's detail (body, outputs) on row hover / keyboard focus, so opening it is instant. Idle time is free bandwidth.

Never show a spinner for <300ms work

A flashed spinner makes fast work feel slow. Delay any loading indicator; if the data lands first, the user saw only the result.

07

Direct answers to your questions

  • Is the local DB where tasks are stored now, saved locally? Yes — a two-file SQLite cache (plaintext skeleton + encrypted title/body). Home paints from it before the network. That's real, and it's why cold start is already fast for layout.
  • Does local storage = speed? For reads, yes, and it's largely delivered. The gaps are: titles don't persist without a keychain (Problem A), and the network reconcile is heavy because it pulls everything (Problem B).
  • Given the DB can be fully encrypted, why memory-only? Because the only way it currently unlocks the encryption is the OS keychain. No keychain → it refuses to write a key → memory-only. The fix is a key ladder (§3) that keeps the file encrypted using the session secret or a passphrase when the keychain is absent.
  • Loading every task, done a month ago or recent? Correct — all=1, no recency cutoff, no limit. Split hot/cold by recency (§4) and cap the first pull.
  • Loading from every group? Correct — no group scope on the wire, though the server supports it and knows your groups. Scope by group (§4, Phase 1) for both relevance and latency.
